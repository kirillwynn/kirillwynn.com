## Decision drivers

- Preserve React Router Data Mode, its raw `Response` semantics, the shared logical route graph, and buffered SSR without Framework Mode or a React Router server package.
- Use Web `Request` and `Response` as the only application-facing HTTP boundary while retaining exact control over Node wire translation and failure behavior.
- Reject ambiguous request framing, untrusted origin or proxy metadata, duplicated security fields, and unsupported HTTP forms before application dispatch.
- Preserve status, redirects, cookies, headers, bytes, HEAD behavior, no-body statuses, backpressure, aborts, and post-header failure safety across the bridge.
- Give the API namespace, document router, mutation transports, error format, and authorization checks one owner each without duplicating routes or business rules.
- Establish nonzero bounded resource limits and deterministic graceful shutdown before deployment values are selected.
- Keep Hono and every server-only transport module unreachable from the browser graph.
- Minimize dependency and adapter surface while avoiding a project-owned application router, middleware composer, and method dispatcher.
- Keep persistence, identity/session/CSRF, editor, worker, media, cache/search, test/CI, and deployment decisions in M07-M14.

## Considered options

### Hono core with no adapter

The candidate is exactly `hono@4.13.3` with the adapter set explicitly **None**. Hono's exact tagged core accepts a Web `Request`, performs route and middleware dispatch, and returns a Web `Response`. That matches the accepted application boundary directly. A project-owned Node bridge still owns the transport details that this ADR must make explicit, so omitting a third-party Node adapter does not create a second application abstraction.

This is selected. It adds one zero-dependency, typed runtime package to the future server manifest while avoiding the exact adapter defect described below. The cost is substantial project-owned HTTP code and validation debt, but native Node 24.19.0 exposes the required strict parsing, raw-header, abort, stream, timeout, and shutdown primitives.

### Hono with `@hono/node-server`

The exact pair `hono@4.13.3` and `@hono/node-server@2.1.1` initially has the smallest apparent Node integration. It is not selected. The tagged listener's response-processing error handler writes `Error: ${err.message}` before destroying the response. Framework `onError` composition and the listener's fetch-error hook do not cover that adapter-time path, while early stream-read errors can also be logged and converted into an empty or partial success. Full buffering would violate the generic streaming contract and still would not cover every response-serialization failure. Selecting the adapter would therefore require a fork, patch, or unsafe error-leak exception.

Because the adapter is not selected, its `serve`, `createAdaptorServer`, `getRequestListener`, `overrideGlobalObjects`, and `autoCleanupIncoming` choices are not part of the implementation. In particular, `serve()` cannot silently choose a port or other M14 concern.

### Fastify

`fastify@5.12.1` is credible and actively maintained, has strong lifecycle and schema facilities, and can send a Web `Response`. It is not selected because the inbound path remains `FastifyRequest` plus raw Node state, default content-type parsing can consume a body before Router handoff, and reply/error/hook semantics form a second HTTP model around the required Fetch boundary. Safely isolating those behaviors would retain nearly all of the project-owned bridge while adding 15 dependencies and framework-specific lifecycle contracts.

### Express

`express@5.2.1` is mature and supported. It is not selected because its Node request/response and middleware contracts require both inbound and outbound translation, its runtime has 28 dependencies, and TypeScript requires the separately published `@types/express@5.0.6` graph. No `@react-router/express`, `@react-router/node`, `@react-router/serve`, body-parser configuration, or Express error pipeline is needed for the chosen Data Mode boundary.

### Native `node:http` only

Using only Node.js 24.19.0 would minimize dependency risk and give complete transport control. It is not selected because the project would also have to create and maintain API routing, method dispatch, middleware composition, framework error dispatch, and distinct not-found behavior. Hono core supplies those application capabilities without owning the Node bridge, so native-only has more first-party application surface without a compensating boundary advantage.

## Decision

### Exact framework and dependency boundary

- Select exactly **`hono@4.13.3`** as the backend/API framework and select the Node adapter set as **None**.
- When a separately authorized dependency-bearing milestone creates `packages/server/package.json`, `hono` is an exact `dependencies` entry of that server owner. It is not installed by this ADR.
- Server code imports Hono through its ESM export. Published CommonJS compatibility is evidence, not the selected runtime path.
- No other Hono adapter, middleware package, validation package, auth package, compression package, Vite integration, or plugin is selected. In particular, `@hono/node-server`, `@hono/vite-dev-server`, `@react-router/node`, `@react-router/express`, `@react-router/serve`, and `@react-router/dev` remain absent.
- Hono, the project-owned Node bridge, server bindings, and server route implementations belong only to the future server graph. The browser build must fail before emission if any is directly or transitively reachable.

### Canonical application boundary and ownership

The one canonical application signature is:

```text
(request: Request, context: ImmutableRequestContext) => Promise<Response>
```

The project wrapper passes the `Request` to exact Hono core dispatch and supplies the immutable context through a server-only binding. That context contains only server-derived request ID, receive time, direct peer metadata, HTTP version, configured public-origin identity, trust provenance, and the exact application signal read from `request.signal`. It is deeply immutable. Raw or forwarded client fields never become trusted synthetic headers or mutable identity claims. The bridge owns a private controller and wire-method state, but neither is exposed as application context.

Ownership is strict:

- Hono owns outer application dispatch, transport-adjacent middleware hooks, the reserved API namespace, API method matching, API 404/405 behavior, and the final document fallback.
- React Router alone owns document matching, loaders, actions, redirects, route errors, route status and headers, SEO data, and stable route IDs over the one accepted logical route graph. Hono must not mirror that graph.
- The reserved API namespace root is exactly `/api/v1`; both that exact path and descendants at the `/api/v1/` path-segment boundary are API requests. The exact `/api` path and its `/api/` descendants are reserved for versioned APIs and never fall through to a document. Breaking representation or behavior changes require a new URI major; compatible additive changes may remain in v1.
- API routes run before the document fallback. An unmatched exact `/api/v1` path or descendant returns an API problem 404; an unmatched document path is decided by React Router and retains its document 404 semantics.
- The document fallback receives the original, unconsumed canonical `Request`. No middleware before it may read, clone, replace, or parse an action body.
- A `Response` produced by React Router is returned from the application boundary without redirect following, status reinterpretation, body decoding, or application reserialization. Only the transport-level safety normalization defined below is permitted.
- The bridge calls the application in process. Internal HTTP loopback, a second route graph, and framework-specific duplication of domain rules are prohibited.

### Inbound Node HTTP to Web Request contract

The production and development hosts use a project-owned Node.js 24.19.0 `node:http` listener. Before creating Web `Headers` or a Web `Request`, the bridge must perform this sequence:

1. The server factory validates every selected option and bounded value before construction. It passes `httpValidation: "strict"`, `joinDuplicateHeaders: false`, `requireHostHeader: true`, `rejectNonStandardBodyWrites: true`, the bounded constructor options, and a synchronous `shouldUpgradeCallback`, but it omits the `insecureHTTPParser` key entirely. The callback is the sole post-parser, pre-event, pre-upgrade-listener gate and must return a boolean without awaiting. Supplying the insecure-parser key even as `false`, selecting `httpValidation: "relaxed"` or `"insecure"`, or launching Node with its insecure HTTP-parser CLI mode is prohibited. After construction, the factory assigns every property-backed limit, including exactly `server.maxHeadersCount = 100`, before `listen`; `0`, post-listen limit mutation, and a fallback listener with weaker settings are prohibited.
2. The native parser is the first count and byte gate. With `server.maxHeadersCount = 100`, exact Node.js 24.19.0 passes `server.maxHeadersCount << 1`, or 200 field/value slots, to its native parser and an over-limit initial-header field produces `HPE_HEADER_OVERFLOW`. The cited regression fixture proves only that initial-header case; the parser resets its header tracking after initial headers, so the same code can occur later while parsing trailers after an `IncomingMessage` was admitted. Neither count nor byte overflow is therefore classified as pre-admission from `err.code` alone.
3. Maintain a FIFO transport ledger per ordinary HTTP socket and a one-way parser terminal state `open -> terminating -> closed`. Every parser-admitted `IncomingMessage` that continues as ordinary HTTP is registered synchronously before any await, dispatch, response write, or middleware: registration is the first action of every `request`, `checkContinue`, and `checkExpectation` path, including an Upgrade attempt that `shouldUpgradeCallback` routes to ordinary `request`. Each entry tracks its private controller, receive disposition through complete trailer parsing, and every queued, committed, or streaming response writer. A normal entry is removed only after receive disposition is terminal and its response emits `finish`; an error path retains an aborted tombstone until the socket is closed, so a settled handler or apparently idle private Node response field cannot erase pipelined work. On the first `clientError`, atomically enter `terminating`. Only if the socket was open and is still writable, the ledger is empty, no queued, committed, or streaming writer exists, and the failed message has not produced an admitted `IncomingMessage` may the transport write once: a minimal sanitized 431 for `HPE_HEADER_OVERFLOW`, or a minimal sanitized 400 for another parser syntax error, followed by close. The eligible syntax code selects the status only after this safe-idle phase gate; any other error closes without a synthetic response. For a trailer or other post-admission error, an active response, or any ambiguous pipelined state, abort or cancel every nonterminal entry exactly once, prohibit every late write, and destroy/close without a synthetic 400 or 431. Repeated `clientError` events never write. No path reflects or logs `rawPacket`, parser text, header names or values, cookies, authorization, or other credentials.
4. After ledger admission, create one private `AbortController`. Require `rawHeaders.length` to be even, compute the field count as `rawHeaders.length / 2`, and build a case-insensitive raw multimap from the complete admitted array before constructing joined Web `Headers`. Validate the entire admitted set, including duplicates at the final allowed position: require exactly one syntactically valid `Host` whose normalized authority is allowed for the selected configured origin; reject every missing, mismatched, or duplicate `Host` and every duplicate `Content-Length`; reject invalid decimal or unsafe `Content-Length`; reject `Content-Length` with `Transfer-Encoding`; and reject duplicated or conflicting `Transfer-Encoding`, `Authorization`, `Proxy-Authorization`, `Cookie`, `Content-Type`, `Origin`, `Forwarded`, or `X-Forwarded-*` fields. Ambiguous framing is a 400 plus connection close, never normalization. The bridge makes no visibility claim about fields on a parser-rejected request.
5. Parse `Connection` only as valid case-insensitive field-name tokens. Remove `Connection`, every field it nominates, and `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade` before constructing Web headers. Transport framing never crosses the application boundary.
6. Accept only origin-form request targets beginning with `/`. Reject absolute-form targets, authority-form targets, `OPTIONS *`, a declared `Trailer` field, and unsupported expectations before application dispatch. The ledger is already registered when `checkContinue` or `checkExpectation` sends an explicit fail-closed 417 without sending 100 Continue. `CONNECT` bypasses `shouldUpgradeCallback`; the project registers no `connect` consumer, so Node fails it closed before application dispatch. In production the callback returns false for every Upgrade. In development it returns true only for the exact Vite candidate defined below; false routes the attempt to ordinary `request`, where this common preflight rejects it before Vite middleware, Web `Request`, Hono, or Router. If undeclared trailers appear or trailer parsing fails, invoke the post-admission ledger abort and close contract without exposing trailers to the application or writing a parser response.
7. Build the absolute request URL from a single configured, validated, allowlisted public origin and the validated origin-form target. Never use `Host`, `Forwarded`, `X-Forwarded-*`, the socket's TLS state, or another client-controlled field to choose scheme or authority. M14 supplies actual origin values; absent, invalid, or ambiguous configuration prevents readiness.
8. Treat forwarding headers as untrusted by default. They do not affect URL, peer address, protocol, authorization, or logs and are removed before application dispatch. A later M14 proxy topology may enable a separately validated chain only when the direct peer belongs to its exact trusted set; no trusted CIDR is selected here.
9. Record the direct socket peer, HTTP version, receive time, configured origin key, and trust decision as pending server-derived context. Preserve raw casing/order only for bounded transport diagnostics; do not copy raw credential or cookie values into logs or application context.
10. Generate a new opaque UUID correlation ID server-side for every admitted request. Ignore any client attempt to choose it, expose it as the sanitized response `X-Request-Id`, and use it for internal diagnostics and problem instances.
11. Retain the wire method only in bridge-private state. Select GET as the canonical application method for a wire HEAD; an ordinary GET also remains bodyless. A GET or wire HEAD with a positive `Content-Length` or any `Transfer-Encoding` is rejected before application dispatch. For other methods, adapt `Readable.toWeb(incoming)` as a byte stream with `duplex: "half"` and enforce the generic byte limit while streaming. A declared or observed over-limit body fails with 413 before any application response commits.
12. Pass the private controller's signal to the `Request` constructor, constructing a wire HEAD as a canonical GET `Request` with no body before any Hono middleware or routing. Fetch may expose a dependent signal, so no identity with `controller.signal` is claimed: store the exact resulting `request.signal` in `ImmutableRequestContext` and use it as the sole application signal through Hono, Router loaders/actions, and downstream in-process work. Never read or compose `IncomingMessage.signal`, and do not infer failure from `incoming.destroyed` alone. A normal incoming `end`, or its `close` with `incoming.complete`, is not by itself an abort trigger. Premature incoming error or close while incomplete, socket or response close before `res.writableFinished`, a framing or size failure, either deadline, parser-ledger termination, and forced shutdown/drain feed one arbitration guard: the first cause aborts exactly once with a typed internal reason, and later causes are no-ops. `res.finish` is the response half of clean ledger retirement: it detaches response-only timers and listeners without aborting, but the entry remains while receive disposition or trailer parsing is nonterminal.
13. The 30-second receive deadline remains armed until body disposition, including trailer parsing, completes. A non-GET/HEAD request starts in `none` when no body is framed or `open` when one is framed, and may transition through `eof`, `draining`, `canceled`, or `failed`; only `none` and `eof` permit connection reuse. If the handler settles while the body is `open`, the bridge retains the ledger entry and performs a bounded drain through the same byte counter and receive deadline before response commit. Drain failure, cancel, limit breach, timeout, framing failure, or a late parser error makes the connection non-reusable, enters `terminating`, closes it, and prevents late or double writes. The 15-second handler timer is cleared atomically when `Promise<Response>` settles; only then does the separate 30-second response-completion deadline govern body cancellation, backpressure, and wire completion.

Ordinary `OPTIONS` for a concrete API path remains subject to that route's explicit method contract. No permissive CORS behavior or trusted proxy range is implied.

### Outbound Web Response to Node HTTP contract

The project-owned bridge, not Hono or an adapter package, transfers the returned `Response`:

- Preserve its status, `Location`, end-to-end headers, and exact body bytes. Do not follow redirects, unwrap route responses, convert binary data to text, or add generic response buffering.
- Extract cookies only with `response.headers.getSetCookie()`. Remove `set-cookie` from ordinary header iteration and pass the extracted values to Node as `res.setHeader("Set-Cookie", string[])`; never comma-join them.
- Strip `Connection`, every connection-nominated field, `Keep-Alive`, `Proxy-Connection`, `TE`, `Trailer`, `Transfer-Encoding`, and `Upgrade` from application responses. Node alone owns wire framing.
- Remove application `Content-Length` unless the transport can prove it equals the unchanged byte count of a fixed representation and the method/status permits it. Remove it after any transformation. Otherwise let Node frame the response. The corresponding GET and HEAD paths apply the same decision.
- For a wire HEAD, use the original bridge-private method only after the canonical GET application call returns its original, potentially body-bearing `Response`. Normalize permitted status, end-to-end headers, cookies, and any exactly proven GET `Content-Length`; then invoke `response.body?.cancel(headDiscardReason)` exactly once for a non-null body before committing Node headers, without obtaining a reader, pulling, or consuming a chunk. Track the cancel promise in a bounded cleanup registry. Cancellation rejection or cleanup deadline is diagnostic-only and bodyless and cannot rewrite the selected status or headers. End the Node response with exactly zero body bytes. This applies equally to API and document responses, raw `Response` values, redirects, 404/405, multiple `Set-Cookie` values, and 204/205/304. Direct `app.fetch` must never observe HEAD: calling Hono with HEAD is prohibited because its exact wrapper replaces the recursively produced GET response with a new bodyless response before the bridge can cancel the original body.
- Write no body for 1xx, 204, 205, or 304; the explicit 205 guard supplements `rejectNonStandardBodyWrites: true`. Application-produced informational responses are rejected because Web `Response` cannot express full informational wire behavior.
- For a non-null body, convert with stable Web/Node stream interop and an abort-aware, backpressure-preserving pipeline. The response deadline and client close cancel the Web reader and downstream work. Do not pre-read chunks merely to infer length.
- If application dispatch fails before headers, emit only a generic sanitized 500: an RFC problem for API requests and the generic document error boundary for documents. If body production or transport fails after headers, cancel the body, close the connection, and record an internal diagnostic keyed by request ID; never append an error string or try to replace committed headers. Disconnect and deadline outcomes are recorded separately and are not rewritten as 500.
- Do not expose a stack, cause, SQL text, schema or table name, filesystem path, secret, credential, header value, or arbitrary `Error.message` to the client. Logs exclude request/response bodies and `Authorization`, `Cookie`, and `Set-Cookie` values.
- Fidelity is guaranteed only within Web `Request` and `Response` capability. Inside the M06 application boundary, request/response trailers, Upgrade, WebSocket, CONNECT tunnels, raw casing/order, and complete 1xx/Early Hints behavior are deliberately unsupported; the separate development-only Vite HMR channel never enters this boundary.

Compression is off in the Hono layer and the bridge. No middleware, proxy, or provider may compress until a later single owner defines byte length, validators, `Vary`, streaming, and failure semantics. M14 may choose the owner; it may not create double compression.

### React Router SSR and development/production integration

- For a document request, the Hono fallback calls the accepted React Router static handler with the original canonical `Request`. A raw Router `Response` returns immediately. Otherwise the project performs the accepted buffered `StaticRouterProvider` render and constructs the document `Response` from Router status and composed end-to-end headers.
- Router status, redirects, expected route errors, document 404, SEO data, hydration data, and route IDs retain their ADR 0002 ownership. Hono defines none of them.
- Buffered SSR remains the baseline. Streaming SSR, deferred loader data, pre-rendering, Framework Mode, RSC, and unstable Router APIs remain prohibited.
- In development, common Node preflight runs first for every ordinary request; Vite middleware mode then receives the native request before application conversion. Only an unconsumed fallthrough reaches the project bridge and Hono listener. The project-owned development host retains ADR 0003's HTML transform, module loading, HMR, and failure behavior.
- The development host constructs the exact project-owned Node HTTP server with the synchronous `shouldUpgradeCallback` and passes that same server as Vite's shared `server.hmr.server`. The host verifies zero `upgrade` listeners before Vite initialization, exactly one Vite-owned listener on that same server afterward, and zero again after `vite.close()`. Project code adds no competing listener, captures or copies no Vite handler, performs no manual delegation, and never calls `handleUpgrade`.
- Vite's standalone HMR HTTP/WS server branch, a separate HMR port override, a Vite-created main HTTP server, and every proxy or plugin upgrade consumer are prohibited. The callback is the only pre-event and pre-upgrade-listener gate; it is synchronous and runs after Node has parsed the candidate `IncomingMessage`, not before HTTP parsing.
- In development the callback returns true only for an exact GET carrying valid, unique `Connection: Upgrade` and `Upgrade: websocket` semantics, the configured HMR pathname, an allowed and unique Host and Origin, the complete raw-header uniqueness and security preflight, and exactly `vite-hmr` or `vite-ping` as the WebSocket protocol. Vite then applies its own applicable token, host, and security gate and alone owns the HMR client set; the project gate neither replaces nor bypasses it. A false result becomes an ordinary request and common preflight rejects it before Vite middleware, Web `Request`, Hono, or Router. `CONNECT` bypasses the callback and fails closed because the project has no `connect` consumer.
- In production the callback always returns false and the server has zero `upgrade` listeners. Every Upgrade attempt therefore reaches common ordinary-request preflight and is rejected, while CONNECT has no consumer. The development exception never enters the M06 Web `Request`, Hono, or Router boundary and selects no application or production WebSocket, concrete port, process, deployment unit, or topology.
- Production imports the built Node ESM server entry and uses the same application and bridge contracts. `vite preview` is not a production server. No port, bind address, process count, TLS, proxy, asset path, provider, container, or deployment unit is selected.

### API, negotiation, and problem contract

- Non-empty successful resource API responses use `application/json`. A valid no-content operation may use a bodyless status. Concrete resources, endpoint inventory, schemas, pagination, search, and cache behavior remain M12 decisions.
- A JSON request body must use `application/json`; unsupported media receives 415, malformed JSON receives 400, and syntactically valid data that fails the public resource contract receives 422. An `Accept` value that permits neither `application/json` nor a wildcard receives 406.
- Every error after request admission and API classification uses RFC 9457 `application/problem+json`. Stable problem types are origin-independent tag URIs of the form `tag:kirillwynn.com,2026:problem/<code>`, paired with the same stable lowercase kebab-case `code`. A semantic breaking change requires a new type and code; no type depends on an unresolved M14 host. A parser response is not a problem document and is permitted only at the safe-idle pre-admission gate: minimal sanitized 431 for `HPE_HEADER_OVERFLOW`, or minimal sanitized 400 for another parser syntax error. Any admitted, active-response, trailer, ambiguous pipelined, or otherwise ineligible parser failure aborts and closes without a synthetic parser response.
- Each problem includes `type`, `title`, numeric `status`, `code`, server-generated `request_id`, and `instance` as `urn:uuid:<request_id>`. `detail` is optional and sanitized. Validation problems may add `errors`, an array of stable public codes and RFC 6901 JSON Pointer `pointer` values; it never names internal schemas, tables, columns, classes, or validators.
- The minimum stable categories are: 400 malformed request; 401 unauthenticated; 403 forbidden; 404 API resource or route not found; 405 method not allowed with an exact `Allow`; 409 conflict; 413 payload too large; 415 unsupported media type; 422 semantic validation failure; and sanitized 500 internal error. Negotiation failure uses 406, request-receive timeout uses 408, and an application deadline before headers uses a sanitized 504. A client disconnect has no synthetic response.
- A 401 carries the standards-required challenge for the authentication scheme later selected by M08; 403 never substitutes for missing authentication, and 404 concealment is allowed only when a later resource authorization contract requires it consistently.
- Hono receives an explicit API-prefix catch-all and a centralized `onError` policy that select these problem objects for API requests. Its default text errors are not the public API contract. Expected Router responses and route errors remain document behavior, not API problems.

### Mutation and authorization-enforcement ownership

- A React Router action or fetcher owns only a mutation coupled to document navigation, document form semantics, redirects, or Router revalidation.
- A resource mutation used by TanStack Query or another interactive client uses the versioned JSON API. One operation has one canonical transport; it is not implemented both as a Router action and an API endpoint.
- Both transports may call one shared in-process command/service. They must not call one another over HTTP, duplicate validation or authorization rules, or let route modules own persistence logic.
- Hono framework hooks may establish request context and must enforce fail-closed denial at the outer/API boundary. Domain services enforce the same authorization server-side at the operation boundary. UI state, a hidden control, Router loader data, or a client cache is never proof of permission.
- Public, authenticated, and preview/private paths and response data remain isolated. A protected operation with missing authentication or authorization context denies; it never degrades to public access. Concrete identity, password, OAuth, session, cookie, and CSRF mechanics remain M08.

### Logical health and graceful lifecycle

- `live` means the runtime has not encountered a terminal internal failure and can execute its lifecycle coordinator. `ready` means initialization and all currently required dependency gates have succeeded, the runtime is not draining, and it may accept application work. These are logical states, not probe URLs.
- Start moves through `stopped -> starting -> running`. Readiness becomes true only after the listener and required gates are ready. Development additionally requires the shared-server HMR listener transition from zero to exactly one Vite-owned listener; startup failure leaves readiness false and closes acquired resources.
- Stop is idempotent and moves `running -> draining -> stopped`: set readiness false and make `shouldUpgradeCallback` reject new HMR candidates first. In development, then await `vite.close()`, Vite client termination, and removal of its sole shared-server `upgrade` listener; only after the listener count returns to zero may the shared Node server close. Production already has a false callback and zero upgrade listeners. Call `server.close()` only after those mode-specific gates, let ordinary active requests drain, and retain abort controllers and ledger entries for every active request.
- At the drain deadline, abort active application work and response pipelines, then use the Node force-close primitive for remaining ordinary connections. Application and production upgrade or tunnel sockets cannot escape this registry because those protocols are rejected; the exact development Vite HMR client set and listener have already closed before shared-host force close.
- Liveness becomes false only when shutdown completes or a terminal fault prevents safe work. New work during draining is rejected rather than admitted to a deadline it cannot meet.
- M14 owns operating-system signal wiring, concrete probe paths, ports, bind addresses, TLS, proxy topology, process supervision, provider health checks, and the final drain value within the allowed bound.

## Consequences

- The application gains a small Web-native routing and middleware framework without accepting a Node adapter whose exact error path can reveal internal messages.
- React Router retains complete document ownership, while the `/api/v1` namespace receives explicit precedence and distinct problem semantics.
- The project must implement and maintain a security-sensitive Node/Web bridge. That is more code than using the rejected adapter, but it makes raw-header validation, origin trust, cookie transfer, no-body handling, aborts, and post-header failure behavior explicit and testable.
- Native Node rejects count- or byte-overflowing initial headers before admission, but header overflow can also occur during post-admission trailer parsing. Only a safe-idle pre-admission failure has no application request ID and may receive the one minimal sanitized parser response; every admitted or ambiguous failure terminates ledger work and closes without a synthetic 400 or 431.
- Application cancellation is represented by the exact constructed `request.signal`, while the bridge retains private lifecycle ownership and treats a clean receive or response finish as completion rather than cancellation.
- Wire HEAD executes the canonical GET application path but makes unused-body cancellation, bounded cleanup, and zero-byte emission bridge obligations instead of relying on Hono's wrapper.
- One exact future server dependency is added to the accepted package graph; the browser graph must continue to fail closed against it.
- Safe finite limits, compression-off behavior, parser-ledger termination, exclusive shared-server HMR ownership, and mode-correct drain ordering become mandatory before deployment topology exists.
- API clients receive stable origin-independent error identifiers and correlation without learning internal implementation details.
- Metadata and tagged-source compatibility remain evidence only. No install, typecheck, build, SSR, HTTP, or runtime capability is claimed.

## Risks

- A project-owned HTTP bridge can contain parsing, smuggling, abort, backpressure, or response-splitting defects. Raw-socket negative fixtures and differential protocol tests are blocking before runtime acceptance.
- `HPE_HEADER_OVERFLOW` covers both count and byte overflow and can occur in initial headers or post-admission trailers. Transport classification must therefore combine code with the complete FIFO ledger, writer state, and one-way socket phase; code chooses 431 versus 400 only after the safe-idle pre-admission gate. Any future Node parser change requires revalidation before changing that mapping.
- `IncomingMessage.signal` aborts on `close` without expressing the bridge's clean-completion distinction. Reading or composing it could cancel valid work after an ordinary receive, so the private controller and explicit completeness checks are mandatory.
- HEAD cleanup that reads, forgets, or cancels the GET body too late can trigger side effects, leaks, or committed-header failures. Exactly-once pre-commit cancellation and bounded diagnostic-only cleanup are blocking bridge properties.
- The Vite HMR exception can accidentally broaden through a standalone server, competing listener, manual handler delegation, permissive callback branch, or callback-false middleware fallthrough. Exact shared-server identity, synchronous callback exclusivity, Vite-only listener ownership, raw security preflight, ordinary-request rejection, listener-count assertions, and ordered teardown control that risk.
- Hono has active releases but no comparable formal LTS end-date policy was found. Exact pins, source review, and ADR 0001 maintenance milestones control drift.
- The selected Hono tag is annotated but not cryptographically verified by GitHub. Registry integrity, provenance, exact commit identity, and later frozen installation are separate required controls.
- Hono core HEAD, error, and route precedence behavior can change across updates. The exact pin and executable boundary tests prevent a documentation inference from becoming a runtime claim.
- Removing an unverifiable Content-Length can reduce efficiency, while retaining a wrong value can enable truncation or desynchronization. Correctness wins unless the bridge has an exact byte proof.
- Conservative limits may reject legitimate future media or long-running work. M11 may define a separate bounded media path, and M14 may tune deployment values only inside the accepted ranges.
- Forwarded metadata remains unusable until an exact trusted proxy topology exists. A deployment that assumes otherwise must fail readiness rather than weaken the default.
- Disabled compression can cost bandwidth. Enabling it before one owner defines validator, length, cache, and stream behavior risks double compression and incorrect representations.
- Stable API categories do not define resource schemas or every conflict. M12 must specialize them without changing the envelope silently.

## Follow-ups

- The independent M06-R1 review remains historical evidence with verdict `Remediation required` and **P0/P1/P2 = 0/2/1**. A fresh independent M06-R2 review must verify both P1 remediations, the P2 source-fragment correction to `#L7-L30`, the exact R2 source identities and cutoff, every retained HTTP/API/security clause, and the absence of implementation or runtime claims. Even a finding-free M06-R2 review does not itself accept M06; acceptance requires a separate Control Tower decision.
- A separately authorized dependency-bearing milestone must recheck exact metadata, add `hono@4.13.3` as the only M06 runtime dependency in the server owner, update the frozen lockfile, and implement the bridge without adding an adapter implicitly.
- M07-M12 must fill their explicitly deferred data, identity, editor, worker, media, resource, and cache contracts without weakening the M06 boundary.
- M13 must choose executable validation and CI enforcement for every listed positive and negative proof, including raw-socket parser and FIFO-ledger phases, signal/body-disposition and trailer phases, bridge-owned HEAD cleanup, and exclusive shared-server ownership of the development-only Vite HMR exception.
- M14 must supply valid public-origin and deployment values, retain untrusted forwarding by default until exact proxy trust is proven, wire lifecycle signals/probes, and keep all limits nonzero and within bounds.
- A later safe adapter, compression owner, trusted-proxy mode, application or production WebSocket/SSE path, streaming SSR, or different framework requires new evidence and, if it changes this decision, a superseding ADR.
